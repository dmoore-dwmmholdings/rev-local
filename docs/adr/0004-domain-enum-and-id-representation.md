# 4. Domain enum and id representation

Date: 2026-08-27
Status: accepted
Item: RL-103

## Context

Every domain enum in SPEC §5 exists in three places at once: a Rust variant, a
SQLite `CHECK (... IN (...))` list, and JSON crossing the engine and MCP
boundaries. Nothing in the type system keeps those three in agreement, and the
failure mode is quiet — a renamed variant writes a different string into a column
whose `CHECK` constraint still allows the old one.

The ids have a parallel problem. SPEC §5 gives every table an `INTEGER PRIMARY
KEY`, so `repo.id`, `run.id` and `finding.id` are all `i64`. Passing the wrong one
is a bug no unit test will catch, because both values are plausible integers.

## Decision

**Enums are generated by a `string_enum!` macro that takes the wire spelling as an
explicit literal**, not by `#[serde(rename_all = "snake_case")]`. The literal in
the Rust source is the same string the SQL `CHECK` constraint lists, so the source
can be read as the authority for what a column may contain, and a variant rename
cannot change the stored value without the literal changing too.

The macro generates `Serialize`/`Deserialize`, `ALL`, `WIRE_NAMES`, `as_str`,
`Display` and `FromStr`. `ALL` is what the round-trip test iterates, so a variant
added tomorrow is covered by that test the moment it is declared.

**Declaration order is the ordering.** `Ord` is derived, and two enums are declared
so the derived comparison is the one call sites actually want:

- `AutonomyMode` is declared `off, dry_run, auto_low_ask_high, auto`, which makes
  SPEC §12.2's "effective mode is `min(global, repo)`" literally `global.min(repo)`.
- `Severity` is declared `info, low, medium, high, critical` — **least severe
  first**, so `findings.iter().map(|f| f.severity).max()` is the worst finding.
  This is the reverse of the order the §10.1 table prints, which is the one
  genuinely confusing thing here; it is called out in the type's doc comment.

**Ids are newtypes with no `From<i64>`.** Construction is always the explicit
`RunId::new(raw)`. Omitting `From` is the load-bearing part: with it, a bare
integer reaches any id-typed parameter through an inferred `.into()`, which is
precisely the mistake the newtypes exist to prevent. `get()` returns the raw value
for the persistence layer, which is the only place that should want it.

## Consequences

- Adding a variant means writing its wire literal, which is the moment to check the
  migration's `CHECK` constraint. That is deliberate friction.
- The compile-fail assertions live in two places: `compile_fail` doctests on the
  `ids` module (cheap, run by `cargo test`) and a `trybuild` suite pinning the exact
  diagnostics. trybuild's `.stderr` files are rustc-version-sensitive; regenerate
  with `TRYBUILD=overwrite` and **read the diff** — a changed message is usually a
  new compiler, but it can be a real weakening of the boundary.
- `Verdict::from_severities` implements the §10.2 mapping next to the types it maps,
  rather than in the pipeline. `info` alone yields `approve`, since §10.1 says an
  `info` finding goes in the summary body and implies no action.

## Alternatives rejected

- **`#[serde(rename_all = "snake_case")]`** — infers the wire string from the
  variant name, which is exactly the coupling this decision removes. It also gets
  `Pr` → `"pr"` right by luck and would get a future `SvnPseudoPr` rename wrong
  silently.
- **A shared `Id<T>` phantom-typed newtype** — one type, seven markers. It reads
  worse at call sites (`Id<Run>` rather than `RunId`) and buys nothing here, since
  the ids have no shared behaviour beyond `new`/`get`.
- **Bare `i64` with naming discipline** — the failure this decision exists to
  prevent.
